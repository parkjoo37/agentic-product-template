# 요구사항 정리

## 결과 파일

`docs/harness/requirements/YYYY-MM-DD-<slug>.md`를 만든다. 같은 날 같은 slug가 있으면 덮어쓰지 않고 번호를 붙인다.

## 문서에 넣을 항목

- 문제와 사용자
- 이번 변경의 결과
- 수용 조건. 각각 관찰 가능한 동작으로 쓴다.
- 범위 밖
- 가정. 질문하지 않고 고른 기본값과 이유
- 열린 위험. `apt-autonomy`에 해당하는 미결정만

## 진행

1. `.harness.json`이 있으면 `profile`을 읽고, 그 프로필 규칙을 수용 조건의 기술 제약으로 반영한다.
2. 위험 결정이 없으면 문서를 저장하고 구현 단계로 넘어간다.
3. 위험 결정이 있으면 그 항목만 질문하고, 나머지 가정은 문서에 남긴 뒤 위험 부분의 구현을 보류한다.
4. 사용자가 이미 수용 조건을 확정했다면 다시 묻지 않고 문서에 옮긴다.
